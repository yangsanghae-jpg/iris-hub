# 입력 탭 상세 설계 — 수집 · 인식 · 1차처리

- 작성일: 2026-07-03
- 지위: REFREEZE의 "입력" 탭 상세. engine/intake(S2)를 UI로 표면화. STORE_SCHEMA(S1) 위에 얹힘.
- 역할 확정(2026-07-03): **입력 = 수집 창구 + 인식 + 1차처리.** 배치 적재·K2 처리는 흐름 탭.
- 원칙: 입력은 "문서를 넣으면 무엇인지 알아보고(인식) md로 뽑는다(1차처리)"까지. LLM 무거운 처리는 안 함.

---

## 0. 입력 ↔ 흐름 경계 (이번 확정)

```
[입력]                          [흐름]
 수집 → 인식 → 1차처리     →    배치 적재 → K2 처리
 (건별·결정적·LLM 없음)          (대량·큐 관리·LLM)
```

| | 입력 | 흐름 |
|---|---|---|
| 임무 | 수집·인식·1차처리 | **배치 적재**·K2 실행 |
| 단위 | 건별(넣는 대로) | 대기열에서 N건씩 |
| 비용 | 가벼움(파싱) | 무거움(LLM) |
| 산출 | 볼트 documents(status=pending) + 추출 md | K2 완료(document_meta·개념) |

- **"배치 크기 100 → 처리 큐"는 흐름 탭 소관** (K2_BATCH_CURATION). 입력은 볼트에 pending으로 적재만.
- 폴더 대량 투입도 입력은 **인식·1차처리하여 pending 적재**, 그 뒤 흐름이 배치로 조금씩 K2.

## 1. 3단계 파이프라인 (입력 내부)

### ① 수집 (3 모드)
- **텍스트 입력**: 외부 LLM 응답·메모 붙여넣기 (본문 무변형 보존). 채널=chat/manual.
- **파일 업로드**: 단일·다중 파일 드롭. 채널=doc.
- **폴더 업로드**: 하위 폴더 포함 대량. 채널=doc. (레거시 10만 건 진입로)

### ② 인식 (파일 유형 판별 — LLM 없음)
문서 유형에 따라 1차처리 경로가 갈리므로 먼저 판별(지난 추출 논의의 triage):

| 유형 | 판별 | 1차처리 경로 |
|---|---|---|
| 텍스트 PDF·DOCX·TXT·MD | 텍스트 밀도 높음 | 경량 파서 (pymupdf4llm 등) |
| 슬라이드·도표형 PPT·PDF | 텍스트+이미지 큼 | 파서 + 페이지 이미지 VLM 병행 |
| 스캔본·이미지 | 텍스트 거의 없음 | OCR / VLM |
| XLSX·CSV | 표 | 표 구조 추출 |

### ③ 1차처리 (추출 → md, 원본 보존 — LLM 없음)
- **원본 보존**: `vault/originals/{channel}/`로 copy-on-ingest (진단툴 A2 역추적).
- **추출**: 유형별 파서로 md 생성 → `vault/extracted/`.
- **적재**: `documents`(status=pending) + `chunks` + FTS 동기. `document_meta`는 비움(K2가 채움).
- **자동 분류 추천**: 규칙 기반 industry/area 초안(선택). 확정은 K2.
- **LLM 요약·개념추출은 안 함** — 그건 흐름의 K2.

대량(폴더)일 때 1차처리는 가벼운 워커가 증분 수행(파싱은 CPU, 결정적). K2 배치와 별개.

## 2. UX 스펙 (확정 목업 기준 2026-07-03)

### 2.1 레이아웃

```
┌ [텍스트 입력] [파일 업로드] [폴더 업로드] ──────────────────────────┐
│ (모드별 입력 영역)                                                   │
│  텍스트 → textarea + 출처/제목/채널                                  │
│  파일   → 다중 파일 드롭존 + 목록                                    │
│  폴더   → 폴더 드롭·경로 + 감지(유형·건수) + 원본보존 옵션           │
│ [인식·1차처리 → 볼트 적재]   "pending 적재 · K2는 흐름 탭에서"        │
├──────────────────────────────────────────────────────────────────────┤
│ 최근 입력  [채널뱃지] 제목 ······ 상태(대기/완료) · 시각             │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 컴포넌트 스펙

| 영역 | 컴포넌트 | 데이터 바인딩(engine/store) | 규칙 |
|---|---|---|---|
| 모드 | 세그먼트 [텍스트][파일][폴더] | UI 상태 | 전환 시 입력 영역 교체 |
| 텍스트 | textarea + 출처·제목·채널 | `intake.from_text()` | 본문 무변형, 채널 자동 |
| 파일 | 다중 드롭존 + 파일 목록 | `intake.from_files()` | 유형 인식 후 1차처리 |
| 폴더 | 드롭·경로 + 감지(유형6·건수) + 원본보존 | `intake.scan_folder()` | 하위 포함, 감지만(적재는 액션) |
| 액션 | [인식·1차처리 → 볼트 적재] | `intake.ingest()` | pending 적재. **배치/K2 아님** |
| 최근 | 채널뱃지·제목·상태·시각 | `vault.recent(n)` | 채널색: doc파랑·chat청록·web앰버 |

### 2.3 정정 (목업 대비)
- 목업의 "배치 크기 100 → 처리 큐" → **흐름 탭으로 이관.** 입력 액션은 "인식·1차처리 → 볼트 적재".
- "원본 보존(복사/참조)" 옵션은 입력 유지(1차처리 산출).

## 3. engine/intake 바인딩 (S2)

```python
# engine/intake/
from_text(text, source, title, channel) -> doc_id
from_files(paths) -> [doc_id]           # 유형 인식 → 1차처리
scan_folder(path) -> {types, count}     # 감지만 (미적재)
ingest(items) -> [doc_id]               # 인식+1차처리+원본보존+pending 적재
recognize(path) -> DocType              # 유형 판별
extract(path, doc_type) -> md           # 유형별 파서/VLM/OCR
```

- store.vault로만 DB 접근. LLM 미사용(요약·개념은 K2/흐름).
