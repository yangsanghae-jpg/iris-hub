# iris-hub 아키텍처 재동결 — 정체성·탭 재편·부족분 보강 (마스터 설계서)

- 작성일: 2026-07-02
- 지위: **마스터 문서.** 기존 부품 설계서 6종(Deck V3 / K2 배치·큐레이션 / Graph V3 /
  OpenClaw / OpenWebUI·L2 / UI-UX)은 본 문서 아래로 정렬된다. 충돌 시 본 문서를 사양으로 삼는다.
- 배경: 원본 `IRIS_V2.5.3_iris_hub_design_freeze`(2026-06-05)는 iris-hub를 "**진도 점검 콘솔**"로
  동결했다. 그 임무(V2.6 Phase 0~5 추적)는 완료됐고, 이후 지식 파이프라인 조각들이 계획된
  정보구조 없이 탭 단위로 누적됐다. 본 문서는 그 상태를 **"데이터 처리 파이프라인"으로 재동결**한다.

## 0. 한 줄 정의

> **iris-hub는 제조업 지식을 "처리"하는 파이프라인이다. 저장이 아니라 처리가 중심이고,
> 처리를 거쳐 쌓인 지식볼트가 최대 자산이며, 그 자산을 검색·탐색·출력·대화로 소비한다.**

원본과의 차이: 진도 콘솔(관측 대상 = Phase 진척) → 처리 파이프라인(관측 대상 = 지식 그 자체).
진도 콘솔의 유일한 생존 조각은 **진단툴 탭**(diagnosis-tool 마이그레이션 진도 관리)으로,
파이프라인과 무관하게 독립 존치한다.

## 1. 계층 모델

```
  ┌───────────────────────── 지식볼트 (최대 자산) ─────────────────────────┐
  │                                                                          │
[입력] ─────→ [처리] ──────→ 정규화·축적 ──┬──→ [뷰어]  위키(검색) · 그래프(관계) │
 · 직접입력     · 흐름         (개념·엔티티   │                                    │
 · WebUI        신규=즉시       1급 객체화)   ├──→ [출력]  PPT                     │
 · OpenClaw     레거시=배치                   │                                    │
     ↑                                        └──→ [대화]  WebUI·OpenClaw          │
     └──────────── 참조(RAG) ───────────────────────  볼트에서 근거 인용          │
  │                                                                          │
  │  [모니터링]  데이터 — 위 전 과정의 현황·품질·상태 (처리·입력의 과정/결과)  │
  └──────────────────────────────────────────────────────────────────────────┘

  [독립]  진단툴 (마이그레이션 진도 — 파이프라인 밖, 그대로 둠)
```

계층별 책임:

| 계층 | 책임 | 원칙 |
|---|---|---|
| **입력** | 지식 원천을 볼트로 들여보냄 | 신규는 즉시 처리 가능, 레거시 대량은 배치로 조금씩 |
| **처리** | 원문 → 분류·요약·**개념/엔티티 추출·정규화** | 파이프라인의 심장. **액션만** — 관측은 여기 두지 않는다 |
| **모니터링** | 처리·입력의 현황·분포·품질 관측 + 큐레이션 | **관찰만** — 실행 버튼은 흐름에 |
| **뷰어** | 볼트를 사람이 소비 | 위키=전문 검색·개념, 그래프=관계 탐색. 역할 분리 |
| **출력** | 볼트를 산출물로 변환 | PPT (마크다운 열람이 아니라 가공된 문서) |
| **대화** | 대화형 입출력 + 볼트 RAG | WebUI·OpenClaw는 입력이자 소비자(이중 역할) |

## 2. 탭 재편 (15 → 9)

**원칙(사용자 지시): 성격을 명료화한 뒤 중복은 과감히 통합, 폐기 대상은 과감히 폐기.**

| 현재 탭 | 명료화된 성격 | 조치 | 계층 |
|---|---|---|---|
| 📥 입력 | 직접 입력(붙여넣기·업로드) + 웹검색 캡처 | **외부응답 흡수** | 입력 |
| 🌐 외부응답 | 웹검색·외부 LLM 응답 캡처 (입력 만들다 파생) | **→ 입력에 통합, 탭 폐기** | (폐) |
| 💬 WebUI | 대화형 입력 + 볼트 RAG | 유지 | 입력/대화 |
| 🦅 OpenClaw | 대화형 입력·지시 실행 + 볼트 RAG | 유지(병행 — 성능 한계 인정, 보조 축) | 입력/대화 |
| 🔄 흐름 | 처리 **액션**(배치·재처리·동기화 실행) | **모니터링 카드 전량 데이터로 이관**, 액션만 남김 | 처리 |
| 📦 데이터 | **모니터링**(현황·분포·품질·큐레이션) | **인사이트 흡수 + 흐름 모니터링 흡수 + 큐레이션 신설** | 모니터링 |
| 📊 인사이트 | 실제론 Grafana/Prometheus/Loki 링크 모음 | **→ 데이터에 관측 링크로 흡수, 탭 폐기** | (폐) |
| 🕸️ 그래프 | 관계 탐색 뷰어 | 유지 (파일 그래프 → **개념 그래프**로, Graph V3) | 뷰어 |
| 📚 위키 | (원래) 전문 검색 위키 / (현재) K2 분류 뷰로 표류 | **재구축 — 개념 중심 검색 위키로 복원** | 뷰어 |
| 📊 PPT | 문서 출력 툴 | 유지 (Deck V3) | 출력 |
| 🦅 Presenton | PPT 계열 중복 | **폐기** | (폐) |
| 🌐 Grafana | 관리 임시방편(개별 개발 시절 잔재), 데이터와 중복 | **폐기** (관측 링크만 데이터에) | (폐) |
| 📚 Obsidian | 기능 이식 시도, 현재 무의미 | **폐기** | (폐) |
| 🔧 진단툴 | diagnosis-tool 마이그레이션 진도 관리 | **그대로 둠** (파이프라인 밖 독립) | 독립 |
| ⚙️ 설정 | 정체 미정(갑자기 생김) | **폐기 — 나중에 성격 정의 후 재추가** | (폐) |

**목표 탭 9종**: 입력 · WebUI · OpenClaw · 흐름 · 데이터 · 그래프 · 위키 · PPT · 진단툴.
폐기 6종(외부응답·인사이트·Presenton·Grafana·Obsidian·설정) 중 2개는 흡수, 4개는 삭제.

## 3. 흐름 ↔ 데이터 분리 (사용자 지시 2 — 전문성 강화)

현재 흐름 탭은 처리 액션과 모니터링 카드가 섞여 있다(대기/처리중/완료/archive 4카드 + K2 단계별
진척 + 안전망 점검 + 동기 점검 + 단계별 흐름 가시화). **"실행하는 곳"과 "보는 곳"이 한 화면에
뭉쳐 전문성이 떨어진다.**

### 재분배 원칙: 명령(command) vs 관측(observe)

| 요소 | 현재 위치 | 이관 후 |
|---|---|---|
| 묶음/개별/선택 처리 버튼 | 흐름 | **흐름 (유지)** — 액션 |
| K2 LLM on/off, 배치 크기 | 흐름 | **흐름 (유지)** — 액션 파라미터 |
| Obsidian 동기화 버튼 | 흐름 | **흐름 (유지)** — 액션 |
| 안전망 점검 버튼 | 흐름 | **흐름 (유지)** — 액션 |
| 대기/처리중/완료/archive 카드 | 흐름 | **→ 데이터** — 현황 관측 |
| K2 단계별 진척(extract/classify/summarize) | 흐름 | **→ 데이터** — 진척 관측 |
| 단계별 흐름 가시화(5카드) | 흐름 | **→ 데이터** — 파이프라인 관측 |
| 산업/시스템 분포, 매트릭스 커버리지 | 데이터 | **데이터 (유지)** |
| 큐레이션 후보·강등 리뷰 | (없음) | **데이터 (신설, §4.4)** |

결과:
- **흐름** = 얇은 실행 콘솔. "무엇을 얼마나 처리할지 정하고 돌린다." 돌린 뒤 상태는 데이터로 가서 본다.
- **데이터** = 지식볼트의 계기판. "지금 볼트가 어떤 상태인가"의 단일 진실 화면. 인사이트(관측 링크)와
  흐름의 모니터링이 여기로 모여, **자산 현황을 한 곳에서** 본다.

## 4. 부족분 보강 — 대과제 완성을 위한 추가 (사용자 지시 4, 내 판단)

방향성 검토(2026-06-09)가 지목한 핵심 결핍: **"지식 단위(Knowledge Unit)가 정의되지 않았다.
문서는 컨테이너일 뿐, 실제 자산은 MES·APS·RTD·Queue Time 같은 개념(Entity/Concept)이다."**

현 코드는 K2가 topics/entities/concepts를 **자유 텍스트 JSON**으로 문서 행 안에 넣을 뿐,
개념이 **1급 객체(자기 페이지를 가진 것)**가 아니다. 그래서 위키가 "개념 위키"가 못 되고
"문서 분류 그리드"에 머물러 있다. **전문 위키를 원한다면 이 층을 반드시 채워야 한다.**

추가는 **새 탭이 아니라 기존 탭의 내부 기능·파이프라인 단계**로 넣는다(탭 감축 기조 유지).

### 4.1 [필수·기반] 개념 사전 + 정규화 — `concepts.yaml`

- 문제: `"MES"`, `"생산실행시스템"`, `"제조실행시스템"`이 지금은 별개 개념으로 파편화.
  이 상태로는 위키·그래프 노드가 갈라져 "전문 위키"가 불가능.
- 해결: canonical 개념명 + alias(한/영/중) 사전. K2 추출 결과를 이 사전에 매칭해 정규화.
  사전에 없으면 **후보 큐**로 보내 사람이 등록.
- 위치: 파이프라인 내부(처리) + 관리 표면은 데이터 탭의 작은 섹션(미매칭 후보 목록).
- 이미 관련 설계 존재: `IRIS_INGEST_NORMALIZATION_RULES.md`(ingest 규칙서)와 `GRAPH_V3_DESIGN.md`가
  **같은 concepts.yaml을 공유**하도록 이미 설계됨 — 본 문서가 이를 정식 채택.

### 4.2 [필수·처리] K2에 개념/엔티티 1급 추출 단계 추가

- 현재 K2 3단계: extract(키워드) → classify(분류) → summarize(요약).
- 추가: 추출된 concept/entity를 §4.1 사전으로 정규화해 **개념 테이블에 upsert**(문서-개념 링크 포함).
- 산출: 개념이 자기 행을 갖는 1급 객체가 되고, "이 개념을 다루는 문서 N건"이 집계됨.
- 이것이 위키(§4.3)·그래프(개념 그래프)의 데이터 원천.

### 4.3 [필수·뷰어] 위키 재구축 — 전문 검색 위키 (사용자 지시 1)

현재 위키 탭(분류 그리드)을 **개념 중심 검색 위키**로 교체:

| 구성 | 내용 |
|---|---|
| **검색창** | 최상단. 볼트 전문 검색 — FTS(이미 DB에 unicode61+trigram dual 구축됨) 우선, 시맨틱(FAISS)은 가동 시 |
| **개념 페이지** | 개념 클릭 → 정의 + 그 개념을 다루는 문서 목록 + 관련(동시출현) 개념 + 신뢰도 |
| **개념 인덱스** | 문서 수(degree) 순 개념 목록 — "가장 많이 다뤄진 지식"이 상단 |
| 문서 열람 | 검색·개념에서 진입한 문서의 요약·원문 |

- **위키(검색·개념) vs 그래프(관계·탐색) 역할 분리**(§7 열린결정 1 해소):
  위키 = "이름으로 찾고 개념 페이지를 읽는다"(텍스트·리스트 중심).
  그래프 = "관계를 시각적으로 훑는다"(노드·엣지 중심). 같은 개념 데이터를 다른 방식으로 소비.
- 전제: §4.1·§4.2가 먼저 있어야 개념 페이지가 성립. 검색만이라면 FTS 표면화로 선행 가능.

### 4.4 [필요·모니터링] 큐레이션 게이트 표면 (데이터 탭 내)

- `K2_BATCH_CURATION_DESIGN.md`(V2.9)의 강등/격리 흐름을 데이터 탭의 한 섹션으로 노출.
- "저장은 관대하게, 전시는 엄격하게" — 저품질 자료는 검색층엔 남되 위키·그래프에선 내려감.
- 배치 대량 처리가 강등 후보를 양산하므로, 데이터 탭에서 주 1회 리뷰(강등/유지 클릭).

### 4.5 [나중·비전 확장] Fact/Relation · Insight — 지금은 안 함

- 개념-개념 관계("MES → integrates → ERP")의 명시적 Fact화, 자동 인사이트 생성은
  v3 아키텍처의 상위 계층(K5 Fact/Relation, K8 Insight)에 해당. **개념층(§4.1~4.3)이
  자리 잡은 뒤** 착수. 지금은 그래프의 동시출현 엣지가 관계의 프록시 역할.

| R2 | 외부응답 → 입력 통합, 인사이트 → 데이터 통합 | 통합 | — |
| R3 | 흐름 모니터링 → 데이터 이관 (§3) | 전문성 분리 | R2 |
| R4 | 살아남은 9탭에 UI-UX 통일 적용 (죽은 탭에 낭비 안 함) | 외관 | R1~R3 |
| R5 | concepts.yaml + K2 개념 1급 추출 (§4.1·4.2) | 기반 | K2 배치 설계 |
| R6 | 위키 재구축 — 검색 + 개념 페이지 (§4.3) | 핵심 가치 | R5 |
| R7 | 그래프 개념 그래프 전환 (Graph V3) | 뷰어 | R5 |
| R8 | 데이터에 큐레이션 게이트 (§4.4) | 품질 | K2 배치 설계 |

R1~R4는 "정리"(구조를 깨끗이), R5~R8은 "완성"(비전 채우기). R1~R3만 해도 체감 혼란의 대부분이 사라진다.

## 7. 열린 결정 (사용자 확인 필요)

1. **흐름·데이터를 두 탭으로 둘 것인가, 한 탭의 두 모드로 합칠 것인가.**
   본 문서는 "명령 vs 관측"으로 **두 탭 유지 + 모니터링만 이관"**을 채택했다. 다만 사용자가
   데이터를 "1·2의 과정/결과"라 본 만큼, 한 탭 두 서브뷰(실행/관측)도 가능. → 두 탭 유지로 진행 가정.
2. **위키 전문 검색의 1차 범위** — 개념 페이지까지 한 번에(R5·R6 묶음) 갈지, 우선 FTS 검색만
   표면화(개념층 없이 선행)할지. 후자가 빠른 가치, 전자가 완성형.
3. **WebUI/OpenClaw를 "입력" 그룹으로 볼지 별도 "대화" 그룹으로 볼지** — 네비 그룹핑 문제이며
   기능에는 영향 없음. 본 문서는 이중역할(입력+RAG)로 기술만 하고 그룹핑은 UI-UX 단계로 미룸.
